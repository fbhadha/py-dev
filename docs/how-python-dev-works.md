# How python-dev works

One document, start to finish, for someone who has never seen this plugin. It explains the pieces, how a repo gets set up, what a working session looks like, and which file to open when you want to change something. Nothing here is the source of truth; every section says where the truth lives.

## 1. The pieces

Four things, in four places.

| Piece | Where | What it is |
|---|---|---|
| The persona | `agents/python-dev.md`, one hand-written file; each harness that needs its own agent-file format gets a copy rendered by `scripts/render_agents.py` | Who the agent is, the loop every message goes through (say what kind of request it is; no ticket, no code), how it talks and pushes back, what it asks before doing, what it refuses, where its knowledge lives. It is the system prompt when you start `claude --agent python-dev` or pick it in Copilot. It holds no procedures, and CI keeps it under 14,000 characters. |
| Our skills | `skills/<name>/SKILL.md` | Nine, loaded only when needed: `py-intake` (set a repo up or re-orient), `py-shape` (an idea to its tickets: the view, the grill, the spec, the tickets with plans; the revision and quick-ticket routes), `py-build` (a ticket to its merge, plan first), `py-review` (the four axes), `py-design` (the craft rules, the order of work, the edges, the fault catalogue), `py-baseline` (what every repo gets, with templates, and the health step), `adk-migrate` (ADK 1.x to 2.x), and two reference packs, `pack-adk` and `pack-data-engineering` (with how-tos and a tested example package). |
| Upstream skills | installed from their maintainers' repos | Matt Pocock's disciplines (domain modelling, TDD, code review, diagnosing bugs, research, prototype, wayfinder, wizard, teach, triage) and Google's ADK knowledge. We call them by name and never copy them. Since 0.11.0 the flow from idea to tickets and the build loop are ours, because his spec and ticket skills leave out file paths and signatures by design and can only be started by a person typing their names. `upstream.json` lists every name we depend on, and the entries of his AI Coding Dictionary the persona links to. Repowise is a CLI tool the persona runs at named moments, not a skill we call. |
| The target repo's files | in your repo, written by `py-intake` | The memory. `AGENTS.md`, `CONTEXT.md`, `docs/adr/`, `docs/howto/`, `docs/architecture.md`, the tool tables, the checks, CI. They work with no plugin installed and are what a new person or a fresh session picks up cold. |

The rule that ties them together: **one place to read each kind of knowledge, one place to write it.** Structure, blast radius, history, health and dead code are read from Repowise. Decisions are written as ADRs. Words are in `CONTEXT.md`. Recipes are how-tos. Rules the machine can enforce are in `pyproject.toml`, not in prose. ADR 0005 in this repository states it.

## 2. How the agent runs everything

You talk; the only commands you type are a few of Matt's skills that only a person can start, and the agent tells you when. The persona opens every session with a status line (version, branch, guards, tracker, next step), then puts every message through one loop: it says what kind of request it is (a new idea, a revision of something already decided, a ticket, a bug, a question, upkeep) and routes it by its table. Anything that would change product code needs a ticket first. Our skills and Matt's model-invoked ones run through the harness's Skill tool. His few user-invoked skills we still route to (`wayfinder`, `triage`, `teach`, `wait-what`, `improve-codebase-architecture`, `setup-matt-pocock-skills`) no harness lets a model start: Claude Code's Skill tool refuses them and Copilot CLI's answers "Skill not found". So when one is due the persona says why, gives you the exact line to type (`/mattpocock-skills:<name>`, from `scripts/find_skill.py --typed` in the scripts folder the session-start hook names), says what it will ask and which answers it will give itself, and waits; typed, the harness loads the skill into the conversation and the persona follows it. Say "you run it" and it finds the file with `find_skill.py` and follows it instead. Type one of his retired flow skills and it first says which of its own steps replaces it and what his leaves out. Repowise runs as a CLI command at the moments the persona names (session start when the index is behind, before editing a file, before naming something new, before review, health on request) and at no other time, because its MCP tools cost ten definitions every turn.

The plugin's hooks run in the session on Copilot CLI and Claude Code, in your project whichever folder the harness starts them in. The rules they hold: `main` changes only by a merge you said yes to, and no product code without a ticket. The agent works on a branch per ticket; a pre-tool hook makes the harness ask you before a commit, merge or push that lands on `main`, and before an edit to `src/` or `tests/` off a ticket branch, and denies destructive git outright; a stop hook refuses to end the turn while ruff is red on files the session changed. VS Code runs none of this plugin's hooks, so there the guards are the repo's own checks. In your repo, CI runs the test-diff check and coverage on changed lines on every pull request, and branch protection on the server (set at intake with your yes) refuses a merge until they are green. `PYTHON_DEV_GUARD=off` silences the ask for one session.

## 3. What a repo gets, and who writes it

`py-intake` runs once per repo and again after a long gap. It never changes an existing file without showing the change and getting a yes for that file; on a repo with history that is one question per file, and a declined change becomes a `later` ticket. This is what it leaves behind:

| File | What it is for | Who writes it after intake |
|---|---|---|
| `AGENTS.md` (`CLAUDE.md` is `@AGENTS.md`) | The rules of work every agent follows, the default one included (no ticket, no code; ideas shaped first; plans in tickets; one branch per ticket), then pointers: read this first, these commands, these rules, these packs. The architecture map, entry points and the current health line are in `docs/agents/repowise-map.md`, a file only Repowise writes, opened when a step needs it rather than loaded every turn. | You or the agent, above the markers; Repowise below. |
| `CONTEXT.md` | The glossary. The words the code, the tickets and the docs share. | Grilling adds a term whenever one is settled. |
| `docs/adr/` | Decisions that were hard to reverse, in Nygard headings with `## Scope` listing the paths each governs. Repowise reads them and warns whoever edits a governed path. | The agent writes one when you make such a decision, then runs `scripts/adr_sync.py`. |
| `docs/howto/add-a-<shape>.md` | One recipe per kind of addition the repo makes, mirroring a real example package that compiles and has a test. | The agent, at intake for the dominant shape, and whenever grilling settles a new shape. |
| `docs/architecture.md` | The layering rules and the composition root. Rules only; the live map is Repowise. | Rarely; when the layers change, with an ADR. |
| `docs/agents/mode.md`, `issue-tracker.md`, `domain.md` | Guide-mode settings; where tickets live and the commands for them; where the glossary and ADRs live. | Intake. |
| `pyproject.toml` tool tables, `.pre-commit-config.yaml`, CI | The checks: ruff, mypy strict, import-linter, module length, secrets at commit on changed lines; tests, README commands and the Repowise change gate in CI. | Intake, from `skills/py-baseline/templates/`. |
| `scripts/repowise_gate.py`, `adr_sync.py`, `run_readme_blocks.py` | The three scripts we maintain: fail CI when a diff makes a touched file worse; bind ADRs to paths; execute the README's command blocks so it cannot rot. | Intake copies them; nobody edits them in the target repo. |
| `.repowise/` | Repowise's index. Gitignored; rebuilt anywhere in seconds. | Repowise. |

### Where the how-tos come from

A **shape** is a kind of addition this repo already knows how to make: another source adapter, another tool, another agent. A how-to is the recipe for one shape, and it must mirror an example package that compiles, so the recipe cannot lie. On an existing repo, intake asks Repowise for the map, finds the most repeated module family, and writes the first how-to from the best existing example of it. On a new repo, the first how-to is written when the first grilling session settles the first shape. A repo that selects a pack shipping how-tos (data engineering: add a source, a transform, a sink, a pipeline) gets them at intake with the pack's example package and its tests, so those shapes exist from the first ticket. From then on the rule is mechanical: a ticket that fits a how-to is built by it; a ticket that leaves the how-to's layers is a new shape, and the agent grills you, extends the how-to and its example first, then builds. Docs first, then code. ADR 0001 states it.

## 4. A session, start to finish

**A new repo.** The agent runs intake: explores and shows you a facts table, sets guide mode, picks the tracker from your remote (GitHub, GitLab, or Backlog.md when there is none), applies the baseline and proves each check bites, indexes with Repowise, writes the docs above, wires the harness shells, commits in named groups, and shows you one report (what is installed, which check stops what and when, what each file is for, how work goes from here, what Repowise found, the first ticket) before asking to merge; the report is the pull request's body, never a file in the tree. Then it shapes your idea (next paragraph).

**Shaping an idea.** Everything new is shaped before it is built, on a `shaping/` branch that holds only decisions: glossary terms, ADRs, research notes, the how-to for a new shape. The agent reads the code first, then gives you its view in one message: the problem, whether it should be built at all, what it would build and leave out, the alternatives it rejected, the risks and one-way doors, the size. Then it grills you in rounds of up to five numbered questions, each with its recommended answer, the reason and what the other answer costs. When a decision waits on a fact from outside the repo (what a library or an API does), his `research` runs as a background reader and leaves a dated, cited note in `docs/research/`; the grill continues. When talking cannot settle a question (how a state model feels, how a library behaves on your data), his `prototype` builds throwaway code on a `prototype/` branch, you react to it, and only the answer comes back as a decision; the prototype stays on its branch as evidence and never merges. When the grill turns up more open questions than one session can hold, a new project or a large feature, his `wayfinder` charts a map of decision tickets on the tracker, one worked per session, research tickets in parallel, until nothing is left to decide; the map then hands off to `to-spec`. Session count decides the route, not project size. In the same session as the grill, the agent writes the spec (the design at the level of modules, types and interfaces, and the order of work) and cuts the tickets: a breakdown table for your yes, then tickets whose plans name the files, the signatures, the tests in the order they get written and the commands. A small idea ends as one ticket built in the same session; a larger one lands the shaping branch on `main` with your yes, hands off, and gets one fresh session per ticket. Changing your mind about something already decided runs the revision route: the agent names what it changes, gives its view, grills only that part, and updates the terms, ADRs, spec and tickets before any code. The hook asks before a commit on a shaping branch that carries product code, because building inside a plan is the failure Matt's own docs report most.

**An existing repo.** Same intake, with two differences. The baseline lands as tickets, one file group at a time, because turning strict checks on over ten thousand lines at once never lands. And before anything else the agent reads the repo back to you from Repowise in six plain paragraphs (what it does, how it is layered, the three worst files and why, what nothing uses, what keeps getting bug-fixed with no decision covering it, which docs point at things that no longer exist) and then grills you on what it found. Every answer becomes a term, an ADR, a dismissed candidate, or a `later` ticket.

**One ticket.** `py-build`: name the shape and check the scope; `repowise why` and `repowise risk` on the files to be touched; search before naming anything new; check the ticket's plan against the code and show it to you for a go; then one slice at a time with `tdd`, tests read-only from red to green, the checks after every green and a line on what each slice added; the full suite, pre-commit and the change gate before review; the review on four axes (`py-review`: Matt's Standards and Spec, Repowise's Change, our Craft through the `py-reviewer` agent); a commit that names the ticket and the decision; the ticket closed; a handoff for the next.

**Upkeep.** The health step, in `py-baseline`, is five Repowise commands and one report in plain words, pointing at the first refactoring target. Tests the user does not trust are classified by `py-design/references/test-audit.md`, with evidence, one action per test. Nothing writes a file; Repowise keeps the history.

## 5. What guide mode means

Before each step the agent says what it is about to do, why it matters here and what you get; after it, what changed and what comes next. Decisions and plans get the full reasoning; commands get a verdict, not their output. `explain:` in `docs/agents/mode.md` turns this up (`teach`) or down (`brief`). It uses the repo's own words. It leads with its view and pushes back: on the premise first (should this be built at all), then on design with evidence (a two-way door gets a recommendation and a move on; a one-way door is never decided on a shrug, and an override is an ADR), and on process (no ticket, scope creep, building without a how-to, skipping the interview on a new shape, weakening a test) it refuses until you state the override in your own words. It asks before pushing to main, deleting, migrating anything but a test database, adding a dependency, changing a public interface, spending money. Unattended runs happen only on a ticket that came out of a grilled spec, and they end in a pull request, never a merge. A step only you can take (an install, a sign-in, an API key, a third-party dashboard) comes as a script his `wizard` writes and you run yourself; no key passes through the chat. A word about AI coding itself (session, handoff, spec, ticket, grilling, smart zone) is defined once, by his AI Coding Dictionary, and the agent gives you the entry rather than its own paraphrase. When you want to learn something properly over several sessions, his `teach` runs in a directory of its own, `~/learning/<topic>`, with that dictionary as its first resource.

## 6. Where to change what

| You want to change | Open |
|---|---|
| How the agent talks or what it refuses | `agents/python-dev.md` |
| What every repo gets | `skills/py-baseline/SKILL.md` and its `templates/` |
| The craft rules or the fault catalogue | `skills/py-design/` |
| What the agent does at session start, and when it runs what | `agents/python-dev.md`, sections 1 and 2 |
| How it shapes an idea, builds a ticket, reviews a diff, measures health | `skills/py-shape`, `skills/py-build`, `skills/py-review`, `skills/py-baseline` (its health step) |
| Intake or the ADK migration | that skill's `SKILL.md` |
| Which upstream skills we depend on | `upstream.json`, then `python scripts/check_upstream_skills.py` |
| Domain knowledge for a kind of repo | a new `skills/pack-<domain>/` in the shape of `packs/TEMPLATE.md` |
| Why something is the way it is | `docs/design/python-dev-agent.md` and `docs/adr/` in this repository |

Before a release: `python scripts/render_agents.py`, `python scripts/check_plugin.py`, `python scripts/test_hooks.py`, `python scripts/check_pack_examples.py`, `python scripts/check_upstream_skills.py`, `claude plugin validate --strict .`, and [the smoke test](smoke-test.md) with a real model on each harness.
