# Research: edge cases, property tests and mutation testing, for 0.12.0

Verified 2026-09-25. The question: how should python-dev find, decide and test edge cases in every ticket, and what do the tools it already pins (mutmut) and the one it adds (Hypothesis) do at their current versions? The method itself is `skills/py-design/references/edge-cases.md`; decision 54 in `docs/design/python-dev-agent.md` records what was decided. This note holds the sources and what was run.

## Mutation on the pack example

The example package (`skills/pack-data-engineering/references/example`, built the way `check_pack_examples.py` builds it): 391 mutants, the whole package in 7.4 s, each module 1.7 to 3.0 s, because mutmut runs only the tests that reach a mutant.

Before this release, with 44 tests that had passed a three-bug hand check (the table above this one): 92 survivors. About twenty pointed at untested edge cases: a tie on `updated_at` in `latest_per_order` (the docstring promises first-seen wins), `amount == 0`, an empty `order_id`, a run with nothing new keeping the cursor in its report, a CSV row with fewer fields than the header, a missing command-line argument, the JSON store's failed-write cleanup. The rest were message text, help text, keyword arguments, SQL keyword case and JSON formatting. One, `astimezone(None)`, survives only where the machine's zone is UTC.

After the edge-case tests and two property tests of this release, 54 tests: 75 survivors, none a missing test. The cleanup path in `JsonCursorStore.save` needs a failing disk and stays untested; the encoding, newline and `astimezone` mutants depend on the machine's locale and zone; the other 68 are noise. The ratio, about three noise survivors for every real one, is why triage has a skip-on-sight list and nothing is gated on a score.
